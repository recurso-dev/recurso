# Recurso Product Quality Bar

## Objective

Recurso should be among the highest-quality financial infrastructure
products in terms of product design, UX, interaction quality,
information architecture and operational clarity.

The benchmark is not visual imitation.

Use products such as Stripe, Linear, Vercel, Ramp and Brex as
references for product craftsmanship.

Recurso must retain its own identity.

---

## Recurso should feel

- precise
- calm
- technical
- premium
- financial
- trustworthy
- operational
- explainable

## Recurso should NOT feel

- like a generic SaaS admin dashboard
- like a dashboard template
- like an AI-generated website
- overly decorative
- card-heavy
- gradient-heavy
- dependent on visual effects

---

## Product depth

A page is not considered high quality merely because it looks good.

A high-quality page must help users understand:

- What is this?
- What is its current state?
- Why is it in this state?
- What changed?
- What financial impact does it have?
- What does it affect?
- What happens next?
- What can I do?
- How can I verify it?

---

## Financial operating system

Recurso's core relationship is:

Customer
→ Subscription
→ Usage
→ Billing
→ Invoice
→ Payment
→ Ledger
→ Reconciliation

The UX should make these relationships discoverable.

---

## Object-centric design

Important objects should feel like workspaces rather than CRUD records.

Important objects include:

- Customer
- Subscription
- Product
- Plan
- Meter
- Usage
- Invoice
- Payment
- Journal Entry
- Ledger
- Reconciliation
- Dunning

Users should be able to move naturally between related objects.

---

## Explainability

Financial numbers should be explainable.

Where appropriate, users should be able to understand:

- how an invoice total was calculated
- why a payment failed
- why an invoice is past due
- why a transaction is unreconciled
- why a journal entry exists

Never fabricate financial explanations.

---

## Progressive disclosure

Show the information required for the current task first.

Expose deeper information progressively:

Level 1:
State + key financial information

Level 2:
Relationships + activity

Level 3:
Financial + technical detail

Level 4:
Raw implementation details

---

## Tables

Tables are operational surfaces.

They should support appropriate:

- search
- filtering
- sorting
- pagination
- column configuration
- selection
- bulk actions
- row actions
- keyboard navigation
- URL state

Do not add columns simply because data exists.

---

## Motion

Motion should communicate:

- state
- change
- progress
- feedback
- causality

Motion must never exist merely for decoration.

Respect prefers-reduced-motion.

---

## Definition of done

A page is not complete because:

- it looks attractive
- tests pass
- it uses reusable components

A page is complete when the user can operate it confidently
and understand the financial consequences of their actions.
